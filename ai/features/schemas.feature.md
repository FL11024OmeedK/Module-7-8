# Feature Spec — Schemas

> Read `ai/ai-spec.md` first. This document adds feature-specific detail.
> This feature has no UI. It is purely a data layer definition used by all other features.

---

## Feature Goal

Define the data structure for the two MongoDB collections used by RE Admin:
- **`agents`** — the real estate agents managed through CRUD operations
- **`users`** — the Rocket Elevators staff who log in to manage agents

These schema files act as the single source of truth for field names and shapes across the entire backend. Every route that reads from or writes to MongoDB must use these definitions — never hardcode field names inline.

---

## Scope

### In Scope
- `agent.schema.js` — defines the Agent document shape and a factory function to build new agents
- `user.schema.js` — defines the User document shape and a factory function to build new users
- Updating `routes/record.js` to use agent fields (`first_name`, `last_name`, `email`, `region`, `rating`, `fee`, `sales`) instead of the tutorial defaults (`name`, `position`, `level`)

### Out of Scope
- Mongoose — this project uses the raw MongoDB Node.js driver
- User CRUD endpoints — users are created manually in MongoDB Atlas, no API
- Password hashing or encryption — plain text password comparison only
- Input validation middleware — validation is handled in each route, not here

## Data + Validations + Expected Behavior

### Agent Document Shape

| Field | Type | Required | Default | Notes |
|-------|------|----------|---------|-------|
| `_id` | ObjectId | Auto | Auto | Generated by MongoDB |
| `first_name` | String | Yes | — | Employee first name |
| `last_name` | String | Yes | — | Employee last name |
| `email` | String | Yes | — | Must be unique per agent |
| `region` | String | Yes | — | One of: North, East, South, West |
| `rating` | Number | Yes | — | Integer 0–100 |
| `fee` | Number | Yes | — | Agent fee in dollars |
| `sales` | Number | No | `0` | Number of sales closed |

### User Document Shape

| Field | Type | Required | Default | Notes |
|-------|------|----------|---------|-------|
| `_id` | ObjectId | Auto | Auto | Generated by MongoDB |
| `first_name` | String | Yes | — | — |
| `last_name` | String | Yes | — | — |
| `email` | String | Yes | — | Used as login identifier |
| `password` | String | Yes | — | Plain text (no hashing for now) |

### Factory Function Behavior
- `createAgent(data)` takes raw request body data and returns a clean, correctly shaped object
- `createUser(data)` does the same for users
- Both functions must explicitly pick only the allowed fields — never spread `req.body` directly
- `sales` defaults to `0` when not provided — callers cannot override this on creation

---

## User Flow

This feature has no frontend interaction. The flow is:

1. A route handler receives a request (e.g., `POST /record`)
2. It calls `createAgent(req.body)` to get a clean, validated object
3. It passes that object to `collection.insertOne()`
4. MongoDB stores the document in the `agents` collection

For users: a developer or coach manually inserts a user document in MongoDB Atlas. No API endpoint handles user creation.

## Notes for the AI

- Place schema files in `server/db/schemas/` — create this folder
- Both files use ES Module syntax (`export`, `import`) — no `require()`
- The factory functions must use explicit destructuring — never `{ ...data }` or `{ ...req.body }`
- In `record.js`, change `db.collection("records")` → `db.collection("agents")`
- In `record.js`, replace all references to `name`, `position`, `level` with the agent schema fields
- Do NOT introduce Mongoose, express-validator, or any new package
- Agents and users are completely separate — different databases, different schemas, different purposes. `agentsDb` connects to the `agents` database. `usersDb` connects to the `users` database. Never mix them.
