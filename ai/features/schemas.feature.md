# 🤖 AI_FEATURE_Schemas

---

## Feature Identity

- **Feature Name:** Schemas — Agent and User Data Models
- **Related Area:** Backend

---

## Feature Goal

Define the data structure for the two MongoDB collections used by RE Admin. These schema files are the single source of truth for field names and document shapes across the entire backend. Every route that reads from or writes to MongoDB must use these definitions — never hardcode field names inline.

---

## Feature Scope

### In Scope (Included)

- `agent.schema.js` — defines the Agent document shape and factory functions to build new and updated agents
- `user.schema.js` — defines the User document shape and a factory function to build new users
- Updating `routes/record.js` to use agent fields (`first_name`, `last_name`, `email`, `region`, `rating`, `fee`, `sales`) instead of the tutorial defaults (`name`, `position`, `level`)
- Renaming the MongoDB collection from `records` to `agents`
- Separating agent and user data into two distinct databases: `agents` database and `users` database

### Out of Scope (Excluded)

- Mongoose — this project uses the raw MongoDB Node.js driver only
- User CRUD endpoints — users are created manually in MongoDB Atlas, no API
- Password hashing or encryption — plain text password for now
- Input validation middleware — validation is handled in each route, not in the schema files

---

## Sub-Requirements (Feature Breakdown)

- Agent Schema — create `agent.schema.js` with `createAgent()` and `updateAgent()` factory functions
- User Schema — create `user.schema.js` with `createUser()` factory function
- Database Separation — export `agentsDb` and `usersDb` as two named exports from `connection.js`
- Route Update — update `record.js` to import `agentsDb` and use agent schema fields throughout all 5 routes

---

## User Flow / Logic (High Level)

This feature has no frontend interaction. The backend flow is:

1. A route handler receives a request (e.g., `POST /record`)
2. It calls `createAgent(req.body)` to get a clean, correctly shaped object
3. It passes that object to `agentsDb.collection("agents").insertOne()`
4. MongoDB stores the document in the `agents` database → `agents` collection

For users: a developer manually inserts a user document directly in MongoDB Atlas. No API endpoint handles user creation.

## Interfaces (Pages, Endpoints, Screens)

### Frontend

- No frontend changes for this feature

### Backend / API

- `POST /record` — uses `createAgent()` to build the insert document
- `PATCH /record/:id` — uses `updateAgent()` to build the update document
- `GET /record` — reads from `agentsDb.collection("agents")`
- `GET /record/:id` — reads from `agentsDb.collection("agents")`
- `DELETE /record/:id` — deletes from `agentsDb.collection("agents")`

## Data Used or Modified

### Agent Document (`agents` database → `agents` collection)

| Field | Type | Required | Default | Notes |
|-------|------|----------|---------|-------|
| `_id` | ObjectId | Auto | Auto | Generated by MongoDB |
| `first_name` | String | Yes | — | Agent first name |
| `last_name` | String | Yes | — | Agent last name |
| `email` | String | Yes | — | Unique per agent |
| `region` | String | Yes | — | North, East, South, or West |
| `rating` | Number | Yes | — | Integer 0–100 |
| `fee` | Number | Yes | — | Agent fee in dollars |
| `sales` | Number | No | `0` | Always 0 on creation |

### User Document (`users` database → `users` collection)

| Field | Type | Required | Default | Notes |
|-------|------|----------|---------|-------|
| `_id` | ObjectId | Auto | Auto | Generated by MongoDB |
| `first_name` | String | Yes | — | — |
| `last_name` | String | Yes | — | — |
| `email` | String | Yes | — | Used as login identifier |
| `password` | String | Yes | — | Plain text, no hashing |

## Tech Constraints (Feature-Level)

- Use the raw MongoDB Node.js driver — do not introduce Mongoose
- Use ES Module syntax (`export`, `import`) — no `require()`
- Factory functions must use explicit destructuring — never `{ ...req.body }` or `{ ...data }`
- `sales` must always be hardcoded to `0` in `createAgent` — callers cannot override it
- `updateAgent` must exclude `sales` so it cannot be overwritten via the edit form
- Agents and users are in completely separate databases — `agentsDb` and `usersDb` must never be mixed
